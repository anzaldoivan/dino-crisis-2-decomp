## Rationale
- Seven tasks, ordered static → runtime → classification → proof → map. T1/T2 (static) and T3 (runtime) are independent; T3 can start as soon as T1 is done or before it. T4 needs the DB to read the loader. T5 needs T3's emulator and T4's classes. T6 (the map + its controls) and T7 (boundaries) consume everything.
- One DB program this phase (`SLUS_012.79`) plus raw overlays imported only as needed for T4/T7 analysis; the round trip (T2) is proven on the exe because that is the milestone's claim; extending it to every overlay is a 1.3/1.5 multiplier, not this gate.
- Ghidra 12.1.3, not 12.1.4: ghidra_psx_ldr 2026.09.03 ships zips up to 12.1.3 only (R1.2-001). The kit was built on 12.1 (`ghidra_import.sh:20`), so 12.1.x keeps the kit scripts' API assumptions.
- GhidrAssistMCP-headless over pyghidra-mcp: the kit's server, stop sentinel and verify script already encode the persistence lessons (`docs/ops/disassembler-mcp.md`); pyghidra-mcp adds a Python+uv dependency for the same delta. Fallback named so T2 never blocks on it.
- PCSX-Redux: the only Lua-scriptable PS1 emulator with an HTTP RAM API and macOS arm64 builds; the kit's `ram_probe.py` already speaks its `/api/v1/cpu/ram/raw`. Port 8081 for the emulator web server, 8080 stays the MCP's (kit default), so both oracles can run together.
- OpenBIOS (bundled) first: no BIOS file exists on this machine; a real BIOS is the developer's supply (Developer decides 2).
- Load map as a generated file (`config/loadmap.tsv`) from a hand-edited evidence ledger (`config/loadmap.evidence.tsv`) + the manifest, with control rows: generated files are never hand-edited (H1), and controls make the map an instrument with a known-true case (G21, lessons "every scanner checked against a known-true case").
- Boundaries checked against a second oracle: `tools/boundaries.py` (own scan) vs Ghidra's switch-table recovery on `SLUS_012.79` must agree on every table (0 disagreements) — two oracles, guess neither (G1).
- Every task `effort: medium` (preset pro, `hard rung: none`). The load-address derivations are the judgment-heavy step; they are split so each piece is routine (T4 ranks statically, T5 proves by bytes — the bytes arbitrate, not judgment).
