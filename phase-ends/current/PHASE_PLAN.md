## Rationale
- Order: census stubs + ledger first (T1) because every later number (wave pools, the milestone) is a denominator from it, and it is free. Pin proofs (T2) before any wave: 1879 of 3426 game fns are refused only for an unproven pin; probing one representative per remaining overlay family is cheap and more than doubles the drawable pool. Wave kit (T3 draw/cards, T4 gate/harvest/ledger) before the manual wave so the manual wave measures the pipeline the campaign will run, not a hand process (DK-43: the first hand-waved boundary is wrong).
- Manual wave = 30 targets, 5 per bucket over six buckets (≤15, 16-50, 51-100, 101-200, 201-400, >400 insns), drawn from the exe/ST/LOGO accepted pool with a fixed seed and no twin of an already-chosen target. 5 per bucket gives a rate resolution of 20% per bucket, enough to locate a cliff that the kit saw move from 86% to 20% across sizes (DK-43); more would spend the Pro budget before routing exists. Every one of the 30 is drafted under the same card and cap so the rate is comparable across buckets.
- Leverage-first campaign (scope line): wave A takes exact-dup families by reach × size first (364 classes cover 1561 fns: one bank plus propagate.py banks the class, fail-closed); wave B the exe and shared engine unique fns below the cliff; wave C the overlays below the cliff; the hard lane (T10) takes above-cliff residuals with the permuter and plateau classifier. Each wave task loops waves until its pool is drained or its context hands off; the wave ledger, not the task count, is the unit of progress.
- T6 is a measurement-and-decision task, not a wave: it projects the remaining campaign from the T5 rate and per-bank cost, sets wave size, and if the projection exceeds one phase it returns `question` with the split recommendation for the critic. Planning the split now would be the guess GENERATION_PLAN.md:34 forbids.
- Tools: one new tool `tools/wave.py` (subcommands draw, cards, gate, harvest, close, --check) + one new record family; three lines (§3): it drives the existing chain per wave and records it; the existing tools filter (draw_filter), prove (probe), bank (reconcile/carve/propagate) and gate (fleet_check) one target at a time; the delta is weight-based draw, deterministic cards, the coverage gate over a directory, the harvest gate and the wave/journal records the milestone checks. Ledger and stub counts go into census.py (it already owns the denominators) rather than a new tool.
- Coder for all tool tasks: opus55 (one tier). Drafting in waves: one coder per target (G41 work dir), briefed from its card; the expert never drafts more than one fn itself (§1 delegation).
- All tasks `effort: medium`: preset `max5` has no hard rung, so the routing-cliff judgment is split into a measurement (T5, machine-checkable rates) and a projection (T6, arithmetic from recorded numbers) instead of one high task.
- `review: yes` on none: bank rate, routing and the wave records are machine-checked; the split, if any, goes through the critic and reaches the developer only if the critic escalates.
- No `## Developer decides` items: stub/ledger definitions, wave size, routing and the split procedure are fixed by PROJECT_CONTEXT.md, GENERATION_PLAN.md:34 and the measured rate.
