# C0048 — Param def sinks to its use in sched1 (birthing boost): give the pseudo a 2nd SET (++n) to keep it on top
tags: codegen-map,sched,sched1,sched2,birthing,insn-order,param,sched-reorg · date: 2026-10-02 · phase/task: 1.7/T4 · origin: -

tell: narrowed-param andi+addiu sunk below the constant loads vs leading the fn (same insns, reordered)
group: sched-reorg

**The residual** — The game fn is `slus_012_79:0x8003E164`. It is a struct init: 13 constant stores and one
`s->f158 = n + 1` of a byte param. The natural draft is `int n; n &= 0xff; ... s->f158 = n + 1;`, or a `u8 n` param.
It has the game's 20 insns and the same registers. But the param's `andi`+`addu` sit after the first two `li`s
instead of leading the fn. This is a pure reorder, words 0-3.

The reproducer is `tools/probes/levers/repro/sched_birth_jal.c` (cc1 `.s`, before maspsx).
`birth_c (n + 1)` gives `li $2,7 | li $3,9 | andi $5,$5,0x00ff | addu $5,$5,1 | sw … | sw … | j $31 | sw $5,12($4)`.
`birth_d (++n)` gives `andi $5,$5,0x00ff | addu $5,$5,1 | li $2,7 | li $3,9 | sw … | sw … | j $31 | sw $5,12($4)`.
The result is the same with a call. `birth_a g(n + 1)` puts the `andi` right above the `jal`. `birth_b g(++n)` leads
the fn.

**The mechanism** — The pinned cc1 runs the old list scheduler `gcc/sched.c`, not haifa. The 2.95.2
configure.in:3552-3557 enables haifa only for alpha/hppa/powerpc/rs6000/sparc/m32r. Also, the `.sched` dump prints
sched.c's own strings (`;; ready list at T-%d:` sched.c:3198, `insn %d has a greater potential hazard` :2140). This
scheduler schedules bottom-up from the block end.

When the scheduler schedules a consumer, adjust_priority (sched.c:1958) raises a ready producer to `max_priority` if
birthing_insn_p (:1922) holds. The condition is a SET of a REG that is live and has `REG_N_SETS == 1`. It holds in
sched1 only. The function returns 0 once reload_completed. The scheduler takes the raised insn next, i.e. places it
directly above its consumer. So the def sinks to its use.
- In the draft (`n + 1`), after combine, pseudo 82 = `zero_extend (subreg:QI a1)` is set once (the entry copy folded
  in). The `plus` writes a fresh pseudo 86. The `.sched` has `;; ready list at T-7: … 48 (7f000001), now 48 45 …` and
  `;; ready list at T-8: … 12 (7f000001), now 12 45 …`. The result is `(insn 12 45 48 …)`: the andi (12) and addu (48)
  sink to the store (50). Then sched2 relays that order (LUID = post-greg order) and puts the two `li`s (15, 20)
  first. The `.sched2` has `(insn 12 20 48 …)`.
- In the lever (`++n`), the `plus` writes pseudo 82 itself. So `REG_N_SETS(82) == 2`, and there is no boost. The
  `.sched` T-7 shows `48 (1)`. The potential-hazard rule (schedule_select :2070) keeps taking stores, and 12, 48 float
  to the block top. The `.sched` order is `12 48 4 15 17 …`, and `.greg` keeps it. The `.sched2` has
  `(insn 12 4 48 …)`, which gives andi, addu, li, li (game order).

The rank order in rank_for_schedule (sched.c:1837) is priority (:1848) > class vs last scheduled insn, 3 classes
(:1851-1876) > lower LUID (:1881). There is no REG_WEIGHT, interblock or depend_count rule. Those rules are
haifa-sched.c:4137-4224, inactive here.

**The lever** — The case is a value derived from a param (or any single-use temp). In our build, the value sits right
above its use, but in the game it leads the block. In this case, give its pseudo a 2nd SET. To do that, update the
variable in place (`++n`, `n += k`, `n &= 0xff` then `++n`) instead of a fresh expression (`n + 1`).

A fresh local (`int m = n; ... ++m` on a `u8 n`) did not match (diff at word 0). This trial was not dumped. In the
inverse case, a def that leads in our build but sits at its use in the game wants a single-set expression.

**The byte proof** — The proof is the `config/levers.tsv` row `multi-set-param`. The file
`tools/probes/levers/multi-set-param.before.c` (`s->f158 = n + 1;`) differs from the game at word 0 (reorder of words
0-3). The `.after.c` file (`s->f158 = ++n;`, the one changed expression) is byte-identical (relocation-masked) under
the pinned triple. The result of `tools/codegen_map.py --check --groups regalloc,combine,sched-reorg` is proven.
