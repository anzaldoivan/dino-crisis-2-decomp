# C0050 — Scaled index: x*4 / p[i] puts the index first in the addu (expand MULT-first swap), but i<<2 keeps base first
tags: codegen-map,expand-cse,expand,fold,operand-order,address,mult,shift · date: 2026-10-02 · phase/task: 1.7/T5 · origin: -

tell: addu operand order in a scaled-index address: index,base vs base,index (same insns)
group: expand-cse

**The residual** — The game fn `slus_012_79:0x800604F4` reads an offset from a table at `base + 8`, with a signed byte
field as the index. Then it does a guarded byte store. The natural draft is `b + *(int *)(b + s->f9f * 4 + 8)`, also
`((int *)(b + 8))[i]` and `((int *)b)[i + 2]`. The draft has the 17 insns of the game and the same registers, but the
address `addu` has its operands swapped. The index register is first and the base is second (word 7).

The reproducer is `tools/probes/levers/repro/expand_commute.c` (cc1 `.s`).
`com_a b + i * 4 + 8` → `sll $5,$5,2 | addu $5,$5,$4 | lw $2,8($5)`.
`com_b b + (i << 2) + 8` → `sll $5,$5,2 | addu $4,$4,$5 | lw $2,8($4)`. `com_c p[i + 2]` (int *p) is the same as
com_a.

**The mechanism** — The mechanism is expand, not cse. Expand fixes the order in `.rtl`, and the order survives `.cse`,
`.gcse`, `.cse2` and combine unchanged. Pointer arithmetic `ptr + int` goes through pointer_int_sum (c-typeck.c:2654).
That function scales the int by the pointee size with a MULT_EXPR (c-typeck.c:2726). Array indexing goes the same way.

In expand_expr, PLUS_EXPR (expr.c:6904) expands that MULT under EXPAND_SUM into a `(mult ...)` rtx. At both_summands
(expr.c:6995), line 7035 swaps that rtx to operand 0: "Put a constant term last and put a multiplication first".
A source `<<` is an LSHIFT_EXPR. Then op1 of the sum is an `ashift`, not a MULT, so there is no swap and the base stays first.
- `com_a .rtl` insn 16 is `(set (reg:SI 86) (plus:SI (reg:SI 85) (reg/v:SI 81)))` (85 = i<<2, 81 = b).
  `com_b .rtl` insn 14 is `(set (reg:SI 85) (plus:SI (reg/v:SI 81) (reg:SI 84)))`. Both have the same insn in `.cse`.
- The game-fn drafts: in the before draft, `.rtl` insn 27 is `(plus:SI (reg:SI 90) (reg/v:SI 82))`. In the after
  draft, `.rtl` insn 25 is `(plus:SI (reg/v:SI 82) (reg:SI 89))`. Both stay unchanged through `.cse`, `.gcse`,
  `.cse2` and `.combine`.
- A pointer temp (`int *o = (int *)(b + 8); b + o[i]`) also matched, but by another route. The `.rtl`/`.cse` dumps
  keep `(plus (reg 91) (reg 85))` index first. Combine re-forms the sum when it folds `85 = 82 + 8` into the address,
  and it emits `(plus:SI (reg/v:SI 82) (reg:SI 91))`. That route is a combine effect, but the shift lever is the
  expand effect.

**The lever** — An address `addu` (or any sum) has index and base swapped against the target, and the index is a
scaled int. If so, change how you write the scale. `i * 4` / `p[i]` puts the index first, and `(i << 2)` added to a
`char *` keeps the base first. The inverse: a game fn with index-first order wants `* 4` or array indexing. The lever
works only for a sum whose scaled operand is a MULT in the tree. A plain `a + b` keeps source order
(fold-const.c:4242 swaps constants only).

**The byte proof** — The row is `shift-scaled-index` in `config/levers.tsv`.
`tools/probes/levers/shift-scaled-index.before.c` (`b + s->f9f * 4 + 8`) differs from the game at word 7 (addu
operand order). `.after.c` (`b + (s->f9f << 2) + 8`, the one changed expression) is byte-identical
(relocation-masked) under the pinned triple. `tools/codegen_map.py --check --groups expand-cse` gives proven.
