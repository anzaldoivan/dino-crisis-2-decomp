# C0004 — A slow gate is a bug: parallel worktrees, a per-binary lock, the parallel flag on every build
tags: gate,parallel,worktree,lock,build,throughput · date: 2026-09-30 · phase/task: - · origin: decomp-architect

A gate that takes tens of minutes per binary is a defect to fix, not a cost to absorb. Drafting is cheap and parallel, but the
byte gate, a build and a hash per draft, is where a campaign's wall-clock goes.

**Why:** on the source project, one binary's gate ran for an hour while thirty-seven finished drafts queued behind it. The
source project once gated sixteen binaries serially to protect one carving job, an hour for what the parallel form did in
minutes. Without `-j`, a single binary's build measured six times slower than with it, byte-identical either way. The belief
was that the gate cost forty to sixty minutes. Clean, it cost fifteen seconds. The stalls were bisects.

**How to apply:** parallel is the default. Each binary gates in its own worktree, under a per-binary lock. The worktree gives
isolation: a carving worker writes only inside its tree. The lock gives mutual exclusion: two lanes never gate the same binary.
Every tool that shells a build passes the parallel flag. A bad parallel build fails the hash, and it cannot bank wrong bytes.

Batch the expensive population behind a strong pre-filter and bisect on failure. Merge carve state so that two workers never
clobber each other. To merge, adopt per-binary files whole and splice a shared registry by block. If you find yourself writing
a serial loop over binaries, stop. That is the hour-long mistake.
